# Open-ended system coverage: evidence gaps and next investigations

**Scope:** audit of the existing research and systems records, 2026-11-10. The video about a settings panel is one illustrative failure case. It does not define the scope, representative distribution, priorities, or expected checks of this project.

A Luna reviewer examined the actual failure cards, system examples, component catalogue, research cells and source routes; another reviewed the 133 planned-cell status/details and existing research tracks. The parent independently checked the recorded system-table counts with `check_system_scope.py`. This is an audit of what those records establish; it is not a proof that no relevant material exists elsewhere in the repository or the world.

## What the system catalogue actually contains

- `research/v2/systems/capability-catalog.csv` contains 62 entries across eight broad families. All 62 are marked `candidate; not exhaustive`, and all 62 use the same generic purpose text. The catalogue therefore offers starting vocabulary but no capability-specific definition, dependency graph, role mapping, failure analysis, or source-backed check for those entries.
- `research/v2/systems/stress-cases.csv` has 18 illustrative system examples; all 18 are explicitly marked `unresearched illustrative decomposition; not exhaustive`. This is not a claim that no related source has been read in another part of the repository.
- `research/v2/systems/compound-research-cells.csv` has 14 cells: 11 queued and three thin discovery records (browser policy, compiler testing guide, and FIX protocol overview). The separate v2 planned-cell table includes other research and must not be conflated with these 14 cells.
- `research/v2/specialization/ecosystem-profiles.csv` has 24 rows, all marked `planned research; not audited`.
- The failure cards include real, bounded evidence beyond UI: cancellation and shutdown, stale async data, database indexes, transaction behavior, payment retry, firmware reset, release artifacts, deployment drift, performance regressions and agent evaluation. They do not yet amount to deep representative investigations across the system universe.

## Concrete gaps that a broad investigation must reach

The examples below are **research prompts and observed gaps**, not an exhaustive taxonomy or a mandate to apply every method everywhere. “Not established” means the reviewed artifacts do not demonstrate the specified work at the stated depth; relevant leads or partial cases may already exist elsewhere.

| System or work context | Existing evidence and concrete gap | Questions and evidence the next investigation must pursue |
|---|---|---|
| Compiler, interpreter, IR and toolchain | The system catalogue names stages/ABI and one compound cell has only LLVM/MLIR guide discovery. The Erlang performance case is not evidence of compiler semantic correctness. | Follow a real source program → language semantics → IR → optimization → machine code → ABI/runtime. Examine optimizer miscompilation, undefined behavior, target differences, debug/release drift and reproducible toolchains. Compare language/specs, actual regression patches, differential or translation-validation tools and applicable workload oracles. |
| OS, kernels, filesystems and drivers | The catalogue lists boot/scheduler/memory/filesystems and a warm-boot driver report remains a reporter hypothesis. The relevant compound cell is queued. | Investigate interrupted updates, crash/power-loss durability, syscall and ABI compatibility, races, driver/device matrix, sleep/resume, isolation and recovery. Distinguish virtual-machine tests from actual hardware and production behavior; follow an actual subsystem’s tests, incidents and specifications. |
| Numerical computing, solvers and geometry | A generic numerical/statistical seed exists; no detailed solver-stability or exact-predicate investigation was found in the reviewed system/failure records. | Examine floating-point conditioning, rounding/overflow/NaN, exact versus approximate predicates, degenerate geometry, solver convergence, reproducibility, uncertainty and hardware variation. Use high-precision references, invariants, adversarial input generation and domain-specialist evidence where appropriate. |
| Codecs, media pipelines and streaming | The catalogue lists codecs, streaming and synchronization, but its media compound cells are queued. The video-modal hover card is an interface symptom, not an investigation of encoding or decoding. | Trace container parsing → codec → timestamps → hardware decode/transcode → network → playback/captions. Inspect real format conformance vectors, malformed/truncated input, resource limits, A/V drift, output fidelity, device compatibility, accessibility and licensing context. |
| Game engines, graphics and GPU work | The game-engine decomposition and renderer/GPU compound cell are illustrative/queued. Nsight appears as a guide excerpt, not a device-fleet validation. | Investigate frame pacing, shader/backend differences, nondeterministic physics, rendering precision, asset import, texture/memory budgets, hardware/driver behavior and gameplay accessibility. Pair actual engine defects and fixes with reference images, performance distributions and platform-specific testing. |
| Firmware, embedded devices and physical control | The nRF52 reset case has project-reported bench evidence; one wireless warm-boot case remains an unverified diagnosis. These cannot stand for all embedded/physical systems. | Trace boot chain, flash writes, rollback, interrupt timing, sensors/actuators, watchdogs, power/thermal margins, manufacturing variation and field recovery. Design safe fault-injection or hardware-in-loop evidence with actual device/revision constraints and domain-specific hazard analysis. |
| Distributed state, databases and recovery | Specific source cases cover stale state, idempotent retries, schema/index mismatch and a transaction/index regression. They are valuable narrow cases. | Follow replication, consistency guarantees, partitions, clock assumptions, retry/replay, transactional boundaries, backup/restore, migrations and data loss. Test state histories with a declared model, fault schedule and correctness oracle rather than generalizing a webhook fix to all distributed systems. |
| Financial systems and marketplaces | Payment and webhook cases cover narrow duplicate-effect risks; an exchange example and FIX source are seeds, not an exchange or regulatory audit. | Investigate order handling, risk checks, matching, ledger invariants, reconciliation, settlement, reversals, chargebacks, disputes, fraud, provider outages and responsible human handoffs. Verify relevant authoritative requirements for the actual jurisdiction and business model. |
| Security, privacy and reverse engineering | Scorecard/OSPS and some security research are sampled; the broad security/privacy/safety campaign remains queued. A tool name is not proof of semantic or safety coverage. | Follow threat model → trust boundary → exploit preconditions → mitigations → verified behavior. Examine cryptography, authorization, supply-chain provenance, data retention, parser robustness, scanner measurement error and reverse-engineering tool correctness in the relevant authorized environment. |
| AI/ML, scientific and data systems | The AI-lab and benchmark notes are comparatively developed, but are largely selected papers and artifact descriptions, with no common independent rerun. | Examine data provenance/labeling/rights, contamination, training/serving correctness, numerical drift, hardware/compute constraints, evaluation validity, uncertainty, scientific reproducibility and model lifecycle; separate first-party claims from independent results. |
| Accessibility, human factors and design | Dialog standards and some WPT sources were read; the general accessibility/design campaign is queued. No browser/assistive-technology lab or disabled-user study was run. | Investigate complete workflows, multiple input and assistive technologies, localization, cognitive and visual needs, user recovery, accessible operations and actual user outcomes. The correct oracle can require people, devices and context beyond the repository. |
| Operations, release, incident and stewardship | Release metadata and generated/deployed drift have concrete cases; the organized operations campaign is queued. | Trace deployment, migration, rollback, observability, incident response, backups/restores, on-call burden, maintenance, end-of-life and archival. Check running artifacts and procedures, not only repository files. |
| Business, governance and support | Role/capability seeds name legal, procurement, billing, support, owners and affected users; a pre.dev pricing heuristic was statically inspected. A comprehensive organizational or economic model has not been established. | Study real decisions, contracts, ownership, costs, documentation, support escalation, dispute/appeal, funding, governance and stewardship across small, volunteer, commercial and public-interest contexts. Treat jurisdictional requirements as context-specific evidence. |
| Source, language and regional reach | Source lists are broad, but C04 and all ten non-English-labelled query-bank records are still queued; one Portuguese Reddit thread was read. | Run native, translated and specialist searches across distinct regional forges, forums, mailing lists, standards bodies and labs. Record access route, exact wording, selection, no-hit scope, original source and contradictory viewpoints; do not equate English search indexing with regional coverage. |

## How to prevent a new narrow scope

1. Decompose each chosen real system recursively into components, interfaces, transformations, owners, resources, deployment and human effects; preserve unknown and unselected branches.
2. Cross system/component × operation/history × failure/property × artifact × lifecycle × role/affected party × environment/workload × source/region/language × evidence/oracle. Track material pairwise and higher-order interactions, not just isolated headings.
3. Select several contrasting research slices before any synthesis; maintain a visible queue for unselected slices. A sample from one ecosystem, one organization, one agent, or one failure family cannot be generalized to the others.
4. For each investigation, trace source → exact claim → implementation or empirical observation → candidate invariant/check → scope, counterexample, cost and false-result limits. Reproduced, author-reported and untested results remain separate.
5. Require a reviewer to choose an omitted component, stakeholder, lifecycle phase and failure mode, then demonstrate whether the evidence trail actually covers it. The reviewer must inspect the contents of records and sources, not just the presence of headings.
6. Continue work outside the above examples whenever an actual brief or newly found specialist domain demands it. The real scope is open-ended; a bounded checkpoint is never proof that all systems or all responsibilities have been enumerated.
