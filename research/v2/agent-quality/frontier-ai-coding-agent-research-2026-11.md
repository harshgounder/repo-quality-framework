# Frontier AI coding-agent and evaluation research — 2026-11-10 snapshot

**Status:** active discovery and source-linked evidence sample. This is not an exhaustive survey of AI labs, papers, benchmarks, or code. Most research items below are 2026 arXiv preprints or first-party reports and have not been independently replicated.

## Why this is a separate research lane

This project needs to understand both the software being evaluated and the evaluation machinery used to make claims about it. Coding-agent research is a useful stress test for the wider repository-quality framework: it exposes problems in repository context, long-horizon state, policy interpretation, test oracles, security, contribution workflows, evaluation validity, and human review. These findings do not automatically generalize to browsers, kernels, firmware, games, medical systems, or other targets. They add candidate dimensions and search routes that must be re-evaluated in each system context.

## Current evidence sample

### Repository-visible security practices and repository health

- **Scorecard practices and npm security outcomes.** [Assumptions to Evidence: Evaluating Security Practices Adoption and Their Impact on Outcomes in the npm Ecosystem](https://arxiv.org/html/2504.14026) analyzes approximately 145,000 npm packages, using 11 OpenSSF Scorecard measures and an aggregate against vulnerability counts and dependency-update timing. Its abstract reports associations of the aggregate with 5.2 fewer vulnerabilities, 216.8 days faster mean time to remediate, and 52.3 days faster mean time to update. The paper uses observational regression and propensity-score matching, not randomized treatment; outcomes rely on disclosed/package dependency data, and the result is bounded to the selected npm/GitHub population and measures. The sample flow, coefficients, uncertainty, sensitivity analyses and package-level validity need a deeper methods/data audit before any quantitative inference.
- **Repository stability measures.** [An Empirical Validation of Open Source Repository Stability Metrics](https://arxiv.org/abs/2508.01358) evaluates a proposed Composite Stability Index on 100 highly ranked GitHub repositories. Its abstract reports that weekly commit-frequency aggregation was more feasible than daily, and median-based issue/PR resolution and review-time statistics fit the examined behavior better than means. This is a check of metric construction and stability in a popularity-selected sample, not proof that the index measures overall quality or predicts project failure.
- **Practitioner health assessment.** The 2026 qualitative study [Assessing open source software health in organizations’ intake processes](https://link.springer.com/article/10.1007/s10664-026-10846-y) identifies 21 health aspects and 72 linked metrics across five areas. Its study used 17 semi-structured interviews: five people from one company and 12 experienced external experts. It also maps the aspects to literature and industry frameworks and applies a selected subset in an organizational case study at a large international automotive manufacturer. The authors report weaker metric support for qualitative aspects and that comparisons should account for life-cycle stage, complexity, governance concentration and the assessing organization’s strategic importance. The interviews were purposive/convenience sampled, and the authors describe the overall interview sample as limited; case-study metric selection was constrained by resources and complexity. This is relevant evidence against a context-free “health score,” not a final metric set.

### What AI coding agents miss or inherit from a repository

- **Bug finding has a difficult oracle.** [PROBE: Frontier Coding Agents Find Different Bugs Than Maintainers Fix](https://arxiv.org/abs/2610.35987), posted 2026-10-26, builds a reference set from 2,457 bugs fixed over 18 months in 20 Python, JavaScript and TypeScript repositories. The paper reports that its best audited agent configuration finds 20.8% of that reference set and no configuration exceeds 8.1% precision against it. It also reports that a human/LLM assessment considered many unmatched findings valid and estimates that a perfect finder could still achieve only 26–47% precision against the partial “maintainers fixed” reference set. Thus reference-match precision and real defect validity are different quantities. The benchmark does not know all valid bugs that were never fixed. The paper points to `LogicStar/probe`, but that repository returned 404 in the connected GitHub contents route and was not found by the bounded repository search; project artifact availability is unresolved.
- **Insecure neighboring code can teach the agent the wrong pattern.** [Coding Agents Propagate Vulnerabilities in Code Bases](https://arxiv.org/abs/2611.11455), posted 2026-11-08, compares secure and insecure repository contexts in 96 backend-generation tasks and 20 C/C++ task pairs across five projects. The paper reports lower secure-and-correct output when insecure examples are present, with effects varying by setting and model; it reports that style-following prompts can increase propagation and security caution prompts reduce it without eliminating it. The linked [ETH SRI repository](https://github.com/eth-sri/vulnerability-propagation) describes the exact task sources, exploit/functionality oracles, `sec_pass` measure and scripts. Its C/C++ setup calls for roughly 400 GB of disk for preparation, a material reproduction cost. The tested repositories and memory-safety/CWE tasks are not a census of code agents or security failure modes.
- **Passing functional tests can still violate project rules.** [SWE-CC](https://arxiv.org/abs/2610.06193) extracts repository-specific contributor policies and evaluates both agent trajectories and final outputs. Its paper reports 823 scored policies across 12 repositories and 500 end-to-end tasks, with agents violating 43.1% of applicable policies; nearly half of violations occur during intermediate steps. The linked [repository and datasheet](https://github.com/dangtruong01/swe-cc-arxiv) disclose important measurement limits: 1,759 extracted policies, 989 in scope, 823 mandatory/scored, 2,603 authored checker tests, 529 approximate checkers, 304 policies never triggered in the 8,000 observed runs, 150 checkers in a dual-annotator audit (94.0% agreement, κ=0.72; 87.2% accepted), single execution per model/task/scaffold/setting, and no release of all historical trajectories or checker-audit records. The authors explicitly say a compliance rate is not a merge-readiness verdict. These details make the dataset a useful source for both candidate gates and gate-limit research.
- **Real workflow misalignment is not identical to benchmark failure.** [How Coding Agents Fail Their Users](https://arxiv.org/abs/2605.29442) analyzes 20,574 sessions from 1,639 repositories across IDE and CLI workflows. The paper defines episodes through observable developer pushback, uses an evidence-filtering extraction pipeline, and reports seven recurring forms/causes. It reports that 90.50% of episodes impose effort/trust costs rather than irreversible damage; visible resolution appears in 9.33% of episodes, and 91.49% of those resolutions require explicit correction. The extraction pipeline's reported human precision is 0.93, inter-rater agreement is 0.78, and LLM-judge accuracy is 0.82. This is observational and selection-bound to the available session corpora; it should not be read as prevalence among all coding-agent users or as a causal comparison among products. Dataset provenance, privacy constraints and exact population boundaries need further appraisal.

### Evaluation can be wrong even when the code and harness run

- **Benchmark tasks can be broken or leak answers.** OpenAI's first-party [SWE-Bench Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations) reviews the 731-task public split. It says a pipeline flagged 286 candidates for deeper review; the report states 200 tasks (27.4%) as broken by the automated analysis and 249 (34.1% of the public split) identified as broken in the human campaign. Five engineers reviewed each task in the human campaign; disagreement and low-confidence cases were escalated. The issue classes include overly strict tests, underspecified prompts, low-coverage tests and misleading prompts. This is a first-party audit by a model provider, and the human process is focused on flagged candidates rather than an independent census of all tasks; preserve that selection boundary.
- Shanghai AI Lab's [SWE-Bench Pro Verified](https://arxiv.org/abs/2609.08149) addresses both reward hacking/leakage and task-quality problems. It reports correcting 102 instances with expert review, code and a released dataset. Some model results fell substantially on the verified set. This is a separate audit and version; its figures should not be combined with OpenAI's audit as if both inspected an identical sample with identical labels.
- Microsoft Research's [Saving SWE-Bench](https://www.microsoft.com/en-us/research/publication/saving-swe-bench-a-benchmark-mutation-approach-for-realistic-agent-evaluation) transforms formal issue text into user-style requests based on telemetry from chat-based coding-assistant use. Its abstract reports benchmark overestimation above 50% for some models on public benchmarks and about 10–16% on one internal benchmark. The change in task framing is important, but the accessible page-level evidence does not provide enough detail here to appraise telemetry representativeness, full task counts or replication.
- Databricks' [internal coding-agent benchmark](https://www.databricks.com/blog/benchmarking-coding-agents-databricks-multi-million-line-codebase) uses tasks from engineers' work on a multi-million-line codebase. The company says candidate tasks and solutions were reviewed by engineers, that every benchmark sample was manually evaluated, and that it rewrote an exact-output test to check behavior because nondeterministic outputs made string matching unfair. It also says the benchmark is not comprehensive and does not publish a generalizable task corpus in the page examined. Its results are useful as a scoped industrial case, not a public ranking.

### Single tasks hide long-horizon, cross-repository and harness effects

- **LoopsBench** (Microsoft-led collaboration) models work as a dependency DAG of separately testable development units; completed units remain regression obligations as later work proceeds. Its [2026 paper](https://arxiv.org/abs/2608.00267) reports 112 tasks across eight languages and nine domains, with 25% task resolution for its strongest evaluated model/harness/outer-loop configuration. The [MIT-licensed repository](https://github.com/microsoft/Loopsbench) says it provides Docker-backed tasks, partial-completion verifiers, an Oracle task check, checksummed task bundles and trusted validation for untrusted task PRs. Those are owner claims from the README; workflow and verifier code were not audited here.
- **CrossSWE** ([paper](https://arxiv.org/abs/2611.01484)) moves from one repository to coordinated changes across 171 real-world instances, 165 repositories, 20 domains and 13 languages. It reports 44.2% of failures involve cross-repository inconsistency, and the strongest reported Pass@1 is 58.48%. This makes interface and change-propagation obligations across repository boundaries explicit. The paper's artifact link and task construction require follow-up.
- **EvoClaw / SWE-Milestone** ([paper](https://arxiv.org/abs/2603.13428), [linked repository](https://github.com/Hydrapse/EvoClaw)) evaluates ordered milestone histories rather than independent one-shot tasks. The paper reports a substantial gap between isolated-task performance above 80% and a maximum of 38% for continuous settings across 12 models and four frameworks. The project README describes seven real-repository histories and a reusable milestone-DAG harness; a second GitHub contents route failed to read the README, so the artifact and its current status still need reconciliation.
- **Harnesses change results.** [Beyond the Model](https://arxiv.org/abs/2609.32459) evaluates ten models from two open-weight families across three benchmarks and finds harness effects depend on task and model; some components improve performance while others reduce it. This supports measuring the model, harness, tools, environment and task together when that is the deployment unit. One paper is not evidence for a universal harness design.

## Research-design implications — explicitly project inference

These sources suggest the future framework research should keep distinct, linked evaluation objects rather than a single repo score:

1. **Artifact and state:** repository, dependency set, build output, deployed copy, release and later evolution state.
2. **Intended outcome:** functional behavior, security, policy compliance, robustness, maintainability, performance/cost, accessibility, reliability, reproducibility, user trust, or other domain-specific properties.
3. **Test/task validity:** prompt/specification, task applicability, expected behavior, reference patch, tests, hidden-test leakage, coverage gaps, and alternate correct implementations.
4. **Agent/workflow configuration:** model/version, harness, tools, context policy, loop strategy, environment, permissions and action history.
5. **Oracle and adjudication:** exact vs approximate checks, outcome/reference matching vs expert validity, human disagreements, untriggered policy, unable-to-assess and `N/A` states.
6. **Time and interactions:** repeated work, dependency graphs, cross-component and cross-repository changes, accumulated regressions, uncertain retries, and user/maintainer correction.
7. **Evidence and scope:** paper/version, task/sample selection, denominator, language/domain, model/harness release, code/data availability, cost, access and independent replication.

Candidate gate mechanisms should therefore be tested for their **measurement target**, not only whether they execute: task and rule applicability, oracle mutation/coverage, counterexamples, independent review or adjudication, side-effect/retry sequences, history-dependent tests, and repeat runs where outcomes can vary. A score is not the ground truth merely because its checker is deterministic. This is an inference to research next, not an agreed product design or universal gate.
