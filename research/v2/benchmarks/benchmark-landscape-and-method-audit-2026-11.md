# Benchmark landscape and method audit

**Reviewed:** 2026-11-10 (Asia/Kolkata)
**Campaign:** C27; planned cells PC117–PC133. Exact searches, index extraction, and source follow-ups are logged in `research/search-log.md`.
**Status:** discovery and selected primary-source appraisal. This is not a unique benchmark census, a validation of every listed suite, or a settled gate design.

## What “hundreds of benchmarks” means here

The first reproducible inventory contains **612 source-index records**, not 612 unique benchmarks:

- **233 entries** from the pinned `tongye98/Awesome-Code-Benchmark` README at commit [`cf177a1`](https://github.com/tongye98/Awesome-Code-Benchmark/tree/cf177a1efc84c1286410200bcf6ec6f7ac4edef2). Its own top-level taxonomy has seven code-task areas and records task, granularity, interaction, and claimed evaluation fields. These are index claims. Every entry remains marked `discovery-index-only`; no entry was promoted to verified merely because the index includes a paper link.
- **379 bibliography-linked list records** from Appendix F of the current [HOW2BENCH v5 paper](https://arxiv.org/html/2501.10711v5#A6). The appendix has **393 comma-delimited label segments** before identity resolution; some rows intentionally group multiple named items. The paper reports analysis of **672 code-related benchmarks**. Its 672 analysis units do not map one-to-one to the 379 appendix rows or 393 raw name segments in the extracted page. We preserve all denominators and have not inferred which is the unique-entity count.

The combined file [`candidate-index-leads.csv`](candidate-index-leads.csv) keeps index row, listed year/category, grouped label, any linked paper/repository/dataset, and the original entry text. It marks alias resolution and primary appraisal as unresolved. A case-folded, whitespace-normalized comparison of `benchmark_name_group` found four repeated labels in the 233-entry catalog and six in the 379 HOW2BENCH rows. The latter include a repeated author-like label (“Lin et al.”), so the count is a parser/identity-review flag, not six confirmed duplicate benchmarks. We have not merged any rows. In the paper appendix, 24 rows did not expose an external paper URL in the extracted bibliography link, and some cited years differ from the appendix year bucket. These are follow-up flags, not proof that the underlying work is invalid.

One widely read example illustrates why index entries need separate paper and benchmark identities: an entry can name **HumanEvalPack** while linking to the **OctoPack** paper that introduced it. That can be correct provenance; the differing labels alone are not a confirmed catalog error. Conversely, a clean-looking title/link pair would not establish that its dataset, harness, tasks, or grader are usable.

## Benchmark families that test different things

The following sources were selected because their mechanisms expose different quality failures. They are not a ranked list. A benchmark’s applicability is conditional on the system, claim, task, oracle, and environment.

## What connects to the user’s modal-path failure example

The video reports different visible close behavior when a settings panel is dismissed through a button versus Escape. That observation supports testing behavior across triggers; it does **not** by itself establish that duplicated code caused the defect. A shared handler is a design choice, not proof that two paths preserve the same behavior.

Transferable test approaches found here:

1. **Specify the behavior contract, then vary the trigger.** Mouse/touch close, Escape, open/close toggle, outside-click, and any supported assistive/voice trigger should check the same state transitions, animation completion/cancellation, focus return, accessibility state, and cleanup. This is a task-specific candidate test, not a universal gate.
2. **Add structural evidence only where the codebase contract calls for it.** NITR’s structural oracles and FrontierCode’s sibling-path/thoroughness criteria can expose behaviorally passing yet incomplete changes. They do not justify banning all duplication.
3. **Try to falsify the tests.** Mutation ideas include omitting the close animation on one trigger, skipping focus restoration, leaving a sibling path open, and cancelling the transition after rapid input. A useful suite should kill relevant mutants and reject invalid mutants separately.
4. **Check the expected behavior independently.** TestJack’s prompt-grounded witness-test pattern starts from the requested contract and checks candidate behavior against it, instead of trusting the existing tests as the sole authority.
5. **Vary the timeline and hidden state.** CUA-Recovery’s delayed takeover and state lineage suggest running tests after intervening actions, rapid repeated toggles, cancellation, re-open, and background updates. This is especially useful when the bug appears only after a sequence or delay.

The point is not that every repository needs every method. The matrix must ask which behavior, artifact, state, risk, and user expectation apply; what oracle can observe them; and what the method cannot detect.

## Cross-cutting mechanism map for the research matrix

The existing open-ended model should represent the following as separate evidence fields instead of a single “test quality” value:

- **Construct and intended claim:** feature behavior, mergeability, maintainability, compatibility, test strength, efficiency, security, physical safety, scientific validity, conformance, or operational recovery.
- **Unit and trajectory:** function, file, repository, multi-repository change, release sequence, long-horizon workflow, user interaction, transaction history, physical scenario, or service trace.
- **Oracle basis:** reference output, tests, property/invariant, mutation, differential/metamorphic comparison, symbolic proof, coverage, rubric/human review, judge model, downstream user result, performance budget, or fault-injection history.
- **Oracle challenge:** known-correct solution, false-positive/negative cases, mutation sensitivity, judge calibration, test-flakiness, hidden requirements, adversarial inputs, bypass attempts, and invalid-task detection.
- **Sampling and leakage:** task source, repository and version, region/language, recency, train/test overlap, public-solution exposure, deduplication, and selection exclusions.
- **Execution contract:** environment/image, dependency snapshot, machine/device, hardware/firmware, API version, resource/time budget, network access, reset/cleanup, state isolation, seed, repetition, and raw trace capture.
- **Outcome reporting:** per-case results, missing/harness failures, confidence intervals or run/task variability, aggregate construction, blocking criteria, unknown/not-applicable handling, and whether the benchmark owner or an independent evaluator ran it.
- **Lifecycle:** versioned task/oracle/environment, drift reports, bug reports, human-gated repair, retired/revised items, migration mapping, rerun evidence, and comparability limits.
- **Use and reuse:** permission/license per artifact, download conditions, runnable/reusable/reproducible status, maintenance/owner status, cost, and sensitivity boundaries.
