## Seed example from the transcript

A speaker describes a settings panel where closing with Escape animates but clicking the close button apparently does not. They hypothesize duplicated closing logic that may diverge over time, and recommend deterministic tools for duplication or related issues. Treat this as a reported behavior and hypothesis from a user-supplied transcript: the actual source code, video, underlying cause and proposed tools were not inspected here. Duplicate code is one plausible explanation, not established fact; lifecycle/unmount behavior, event propagation, timing or CSS/state differences could also cause it.

The general investigation: discover paths that should implement the same user intent, identify the observable contract for each and examine where they can diverge. A shared semantic operation can reduce drift when the operations really have equivalent semantics, but literal code reuse is not a universal requirement: accessibility behavior, focus restoration, input-specific affordances, reduced-motion settings and intentionally different behavior may matter. Avoid forcing distinct contexts together or creating a needless abstraction.

## Additional evidence from current benchmark and lab work

The C25 paper/repository pass strengthens this failure-pattern track without diagnosing the supplied video:

- [RepoNorm](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) mines and verifies explicit and implicit repository norms using source evidence, history and counterexamples. [SWE-CC](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) checks policy compliance across the agent's work path and final contribution. These mechanisms suggest that a repository may contain more useful contracts than the ticket or standard test suite exposes.
- [All Smoke, No Alarm](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) finds test-file presence and syntactic assertion signals can overstate verification strength. An assertion must be judged against the intended property and a test's ability to catch a deliberately introduced divergence; assertion count is not an oracle-strength measure.
- [SWE-Maintain](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) separates new code's later maintenance effect from already-failing inherited tests. Its result is counter-evidence to a blanket “agent code is harder to maintain” claim in that Python benchmark.
- [CrossSWE and InfraDev](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) expose failure surfaces that a single-repository, unit-test pass can miss: cross-repository contract drift, numerical/state errors, resource behavior, and claimed performance that was never measured. [Infrathon](../research/v2/agent-quality/current-lab-artifacts-and-frontier-evidence-2026-11.md) adds multi-hour optimization as a distinct workload and cost class.

These are author-reported benchmark mechanisms and outcomes. No source task was reproduced, no check or stress test was run, and no new universal gate is supported. Future investigation should select a real task and its applicable invariant before choosing duplication detection, mutation testing, integration/state-machine tests, fault injection, or a domain workload oracle.

## Starting hypotheses for exploration, not verified findings or an exhaustive taxonomy

- Semantic behavior spread across separate entry points, duplicated validations, permission checks, error handling, serialization, business rules or state transitions.
- Inconsistent assumptions at boundaries: API versions, timeouts, encodings, units, schemas, precision, ownership, serialization, protocol states, platform behavior or language bindings.
- Race conditions, stale or partial state, retry amplification, non-idempotent operations, cancellation, duplicate delivery, transactional failures and recovery paths.
- Error paths and exceptional inputs: malformed/truncated data, resource exhaustion, rare combinations, extreme values, clock changes, locales and unexpected ordering.
- Tests that miss meaningful behavior: excessive mocks, shared bugs in tests and implementation, weak assertions, flaky timing, missing operational or user conditions, compatibility and integration blind spots.
- UI and accessibility discrepancies among input methods, state, focus, asynchronous updates, animation timing, motion preferences and assistive technology.
- Specialized engines and physical/low-level systems: numerical stability, geometry degeneracies, parser differentials, firmware power loss, hardware timing or resource constraints. Applicability depends on the real system.
- Maintenance and architecture: hidden dependencies, drift across generated and hand-written code, unsafe defaults, accidental complexity, wasteful work and regressions after an apparently local change.

These are leads for critical investigation; do not represent this list as a surveyed catalog or apply every pattern to every system. Avoid equating duplicated text with a defect: separate independent requirements can legitimately look alike, and premature abstractions can increase coupling.

## Pattern record and concrete outputs

For each researched pattern maintain a stable linked record, adapting existing v2 files instead of inventing an isolated competing dataset. Record: ID and name; real source/version and precise locator; context and affected system/components; symptom; prerequisites; causal mechanism and confidence; triggering change; user/operational impact; concrete minimal reproduction or justified inability to reproduce; relevant invariants and intended vs intentional differing behavior; applicable scopes and counterexamples; candidate detection approaches and tool versions; limitations, false positives/negatives, cost and access; competing explanations and sources; evidence status; verification results; unresolved questions; and links to research runs, roles, checks and coverage cells. Do not store unlicensed or sensitive source data indiscriminately; link and describe under appropriate terms.

For each well-supported pattern, compare static clone/structural and semantic analysis, language-aware rules, type/static analysis, runtime instrumentation, contract/invariant tests, integration and end-to-end tests, property-based and metamorphic tests, fuzzing, differential testing, model/state-machine testing, concurrency/fault injection, stress/load testing, visual/accessibility testing, mutation testing, targeted manual or specialist review as appropriate. These are candidate methods, not a prescription to run all methods for every pattern. Research actual implementations, rule behavior, inputs, versions, language support, reproducibility, cost, and independent evaluations before recommending a tool. A deterministic detector may be stable yet still miss bugs or produce false alarms.

Where feasible build a small authorized, safe, reproducible fixture with a known defective variant, expected behavior and a legitimate counterexample; run selected checks, record commands/versions/results and show whether they detect the defect without wrongly flagging the counterexample. Mutation testing is one possible way to probe the test's sensitivity; surviving mutants and equivalent mutants require interpretation. Distinguish unrun proposals from demonstrated findings. Do not run untrusted code, production stress tests or destructive experiments without appropriate isolation and authorization. Respect system safety and user data.

Integrate findings as conditional quality questions or candidate gates only after inspecting evidence, scope, false results, tradeoffs, severity, burden and ownership. Separate discovery, research, demonstrated checks and enforced gates. A proposed rule must have documented applicability, legitimate exceptions and what to do when evidence is unavailable; don't create a universal duplication ban, score or blocking gate. The desired final outcome is a growing, traceable library of mechanisms and context-sensitive methods, not a count of patterns or tools.
